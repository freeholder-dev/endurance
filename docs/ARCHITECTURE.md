# Architecture and decisions

Endurance is a Quattro plugin with a resident `service` and a `bar-widget`. The service starts one Python standard-library process each minute. It reads `/sys/class/power_supply` and `/proc`, records one SQLite transaction, and exits. The bar widget reads a bounded JSON snapshot every 30 seconds and renders a compact Omarchy `KeyboardPanel`. Neither component starts another Quickshell instance. The packaged shell remains untouched.

The first sample after installation or reboot is explicitly marked **start first observed**, because the actual unplug time is unknown. A session is only marked **unplug detected** after the recorder previously observed AC on the same boot within five sampling intervals. A session ends on observed AC reconnection. After reboot, an open session is closed at its last sample and marked interrupted; it is excluded from the median. Shell restarts retain the same open session and process baselines in SQLite. If the shell is stopped throughout a full unplug/replug cycle, there is no evidence from which to reconstruct it.

Wall duration is reconnect time minus unplug observation time. On Linux, `CLOCK_BOOTTIME` advances in suspend while `CLOCK_MONOTONIC` does not. Their difference between samples estimates suspended time; awake duration is wall duration less that amount. The end observation accounts for the last interval. More than five minutes of unmonitored awake time closes the session at its last sample as a monitor gap. AC first observed after a long sleep is labelled separately and excluded from the median, because the exact reconnection time is unknown. Clocks cannot reconstruct sleep or power events across a reboot.

Energy uses `energy_now`/`energy_full` where exposed. The test Dell only exposes `charge_now`, `charge_full`, and `voltage_now`, so the backend estimates Wh as Ah × current V and labels it approximate. Voltage changes with load and state of charge, so this is not coulomb-counter energy. `power_now` is preferred; `current_now × voltage_now` is the fallback. Endurance does not guess a remaining runtime from one unstable instantaneous reading.

Per-process `/proc/<pid>/stat` user plus system CPU ticks are sampled every minute and aggregated by process name. PID plus process start ticks prevents PID reuse from corrupting deltas. The UI calls this **CPU activity proxy · experimental**, with percentages of observed CPU ticks. It is **not** a measured energy split: idle power, display, GPU, memory, I/O and kernel work are not attributed. Processes that start and exit between samples are missed. Intel RAPL `energy_uj` exists on the test machine but is root-readable only; v1 does not require privilege. UPower is part of Omarchy's native power UI, but `/sys` gives this recorder direct, low-overhead, unprivileged battery data. A database and telemetry architecture are retained for future attribution research without inventing precision now.

On the development Dell, ten unprivileged `/proc` scans had a 1.06 ms median and 1.59 ms maximum. Scans occur only while on battery, once per minute. This is an execution-time check, not a measured battery-life impact.

The stock Omarchy power panel already provides battery percentage, profiles, and system stats. [Battery Usage](https://github.com/OverStyleFR/omarchy-battery-usage) focuses on live draw and short-window graphs; [Omarchy Power](https://github.com/austrasien/omarchy-power) extends the power panel with health, short watt history, CPU, profiles and power controls. Endurance focuses on session history and comparison. It does not change stock power profiles, alerts, or hardware settings.

The database is `${XDG_STATE_HOME:-~/.local/state}/endurance/history.sqlite3`. It is created with a user-only state directory. Plugin removal leaves history in place, so uninstall does not silently erase personal data.
